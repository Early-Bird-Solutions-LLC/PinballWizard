# 0038 — Cloudflare Origin CA certificate for the ACA origin (retire auto-renewing managed cert)

**Status:** Accepted
**Date:** 2026-06-18

## Context

`pinwiz.ai` is served through Cloudflare (proxied apex CNAME — confirmed live: the apex resolves to Cloudflare edge IPs, not the Azure Container Apps ingress). The Wizard Container App `pinwiz-ca-wizard-dev` was bound to its custom domain with an **Azure-managed (Let's Encrypt) certificate** using HTTP domain-control validation ([ADR-0028](0028-cloudflare-iac-via-opentofu.md) covers the Cloudflare IaC; the managed-cert binding was the interim Phase-7 setup).

On 2026-06-18 Azure Advisor raised a **High**-impact recommendation: *"An issue has been detected that is preventing the renewal of your Managed Certificate."* The managed cert was issued ~2026-05-15 (90-day lifetime, renewal attempts begin ~45 days before expiry) and the auto-renewal is now failing.

**Root cause.** A managed certificate renews via a domain-control challenge against `pinwiz.ai`. Because the apex is a *proxied* Cloudflare record, that challenge lands on the Cloudflare edge (behind the WAF) and never reaches the ACA ingress that must answer it. The `asuid.pinwiz.ai` TXT verification record and the CNAME are both present and correct — Azure's generic "verify your DNS settings" text is misleading. Initial issuance succeeded on 2026-05-15 because a dashboard-created "ACME bypass rule" was in place; that rule was **not carried into the IaC migration** the next day (2026-05-16), so the validation path that worked at issuance no longer exists. This will recur every renewal cycle as long as an ACME-renewed cert sits behind the Cloudflare proxy.

A 15-year **Cloudflare Origin CA certificate** (valid for `pinwiz.ai` + `*.pinwiz.ai`) already exists — it is generated by the `infra/cloudflare` OpenTofu stack and exposed as the sensitive outputs `origin_certificate_pem` / `origin_private_key_pem`. It was never installed on the origin; the zone's `ssl=strict` setting was therefore documented as "pending cert install." (The setup doc also incorrectly claimed the cert/key were already in Key Vault — they were only ever in tofu state.)

## Decision

Bind the Wizard custom domain to the **Cloudflare Origin CA certificate** instead of an Azure-managed certificate.

- The Origin CA cert + key are read from their tofu-output PEM form, packaged into a PKCS#12/PFX with `openssl pkcs12 -export`, and imported into Key Vault `pinwiz-kv-dev-buutj` as the certificate object `cloudflare-origin-pinwiz`, by an idempotent operator script (`infra/scripts/Import-OriginCaCertToKeyVault.ps1`). PFX is Key Vault's native cert+key container and the format Microsoft's samples use; it sidesteps the constraints KV places on PEM import (private key must be PKCS#8 — but `tls_private_key` emits PKCS#1 — plus UNIX line endings and cert-before-key ordering, per the KV "Formats of import we support" doc). This is a data-plane operator action, not Bicep (ARM/Bicep cannot import certificate content), because the source material lives in tofu state, not in source control — and the key must never be committed. The operator running the import needs **Key Vault Certificates Officer** on the vault (the Bicep dev-RBAC grants Secrets Officer, enough to *read* the backing secret, but not certificate *write*); this is a one-time bootstrap grant rather than a Bicep role assignment, because a Bicep grant plus the `wizardOriginCert` resource would be circular on a fresh environment (the cert must exist in Key Vault before the resource that references it can deploy).
- A `Microsoft.App/managedEnvironments/certificates` resource references that Key Vault certificate via `certificateKeyVaultProperties` and the existing `acaIdentity` user-assigned managed identity (which already holds Key Vault Secrets User). The Wizard custom-domain binding switches to `SniEnabled` against this cert.
- The Azure managed-cert resource (`wizardCustomDomainCert`) and its two-pass `wizardCustomDomainCertReady` scaffolding are removed. A Key-Vault-sourced cert value is available at deploy time, so there is no ARM circular dependency and no second pass is needed.
- The Cloudflare zone's `ssl=strict` mode — already set — becomes legitimately correct: the origin now presents a Cloudflare-trusted certificate.

## Consequences

**Positive:**

- The renewal-through-the-proxy failure is eliminated permanently. Nothing has to complete an ACME challenge through Cloudflare ever again; the Advisor recommendation clears once the managed cert is gone.
- `ssl=strict` is now correct end-to-end, closing the long-standing "pending cert install" gap and removing the `ssl=full` stopgap from the documented plan.
- The custom-domain binding is single-pass — simpler Bicep, no `wizardCustomDomainCertReady` flag to flip across two deploys.
- The cert→Key Vault path is captured in a committed, idempotent script, so it is reproducible rather than a one-off manual action.

**Negative:**

- The origin certificate is browser-untrusted **by design** — it chains only to Cloudflare's edge. This is correct for a Cloudflare-fronted origin (clients never see it; only Cloudflare connects to the ACA ingress), but it means hitting the ACA FQDN directly in a browser shows an untrusted cert. The WAF host-header rule and (future) Authenticated Origin Pulls are the controls that discourage direct-to-origin access.
- Certificate renewal becomes a 15-year / manual concern rather than automatic. Tracked as a secret-rotation follow-up; a 15-year horizon is acceptable for v1.
- The cert/key transit a local machine during packaging. Mitigated: the script holds them only in temp files that are securely deleted in a `finally` block, and never logs key material.

**Deferred (out of scope):**

- **Authenticated Origin Pulls (AOP) enforcement at the origin.** AOP is enabled on the Cloudflare side but not enforced at the ACA ingress. True enforcement requires ACA `ingress.clientCertificateMode` plus app-level validation of Cloudflare's client certificate — a separate, larger piece. Left as a tracked follow-up; this decision is server-cert only.

## Alternatives considered

- **Keep the managed cert; un-proxy the apex (DNS-only) during renewal, then re-proxy.** Rejected: fragile, recurs every ~90-day cycle, requires manual DNS toggles or a re-added ACME-bypass WAF rule, and conflicts with the documented Origin CA target. It treats the symptom, not the cause.
- **Keep the managed cert; permanently re-add a Cloudflare ACME-bypass rule** so `/.well-known/acme-challenge/*` reaches the origin. Rejected: still depends on ACA serving the challenge through the proxy on every renewal, keeps a Let's Encrypt dependency for an origin that only Cloudflare ever talks to, and adds a standing WAF carve-out.
- **Inline base64 PFX as a Bicep/param value.** Rejected outright: puts private key material in source/parameter files (and git history), violating the no-secret-in-source invariant.
- **Automate the cert→Key Vault import inside the Cloudflare tofu stack.** Rejected for v1: it would force the Cloudflare stack to take an `azurerm` provider and Key Vault write scope, expanding that stack's blast radius and credential surface for a once-per-15-years action. A documented idempotent operator script is the proportionate choice.
